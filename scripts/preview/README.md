# Staging preview operations

The `Staging preview` workflow on `main` supports `deploy`, `list`, `rollback`, and `release` for slots 1–6. Deploy an existing same-repository branch and select a slot. The workflow summary gives the selector for `X-Status-Preview` and its commit. Slots are leased for 48 hours from a successful deployment, and only the owning branch can update, roll back, or release an active slot. After expiration a new branch can claim it. Use the browser launcher to inject the selector on staging requests.

The routing switch `status-preview-enabled` must be enabled in Flagship. Provision `status-preview-slot-1` through `status-preview-slot-6` as JSON flags with a `current` variation whose initial value is `{}` and default variation `current`. Each slot has two preprovisioned stacks named `status-preview-<slot>-<a|b>-<component>`. Components are `gateway`, `operations`, `status-api`, `monitoring-api`, `status-ui`, `admin-ui`, and `probe`. A reviewed subscriber-capable branch additionally deploys a private `subscriber` Worker per stack. Configure the main gateway with a service binding to each stack gateway. Provision staging secrets on the corresponding preview Workers before use. Probe schedules must remain empty.

Create a GitHub Actions environment `staging-preview`, restricted to `main`, with these values:

- Variables `FLAGSHIP_APP_ID` and `CLOUDFLARE_ACCOUNT_ID`.
- Secret `CLOUDFLARE_PREVIEW_API_TOKEN` scoped to editing only preview Workers, reading the staging D1 migration table, writing the staging Flagship app, and, when subscriber scheduling is enabled, writing the staging D1 scheduler fence.
- Secret `PREVIEW_STAGING_CONFIG` containing JSON with string fields `d1DatabaseId`, `d1DatabaseName`, `accessTeamDomain`, `accessAud`, and `endpoints`. Optional fields `uiMode`, `apiVars`, `statusApiVars`, `monitoringVars`, `probeVars`, `vpcServices`, `extraServices`, and `resourceBindings` carry the relevant staging configuration. `extraServices` maps `api`, `statusApi`, `monitoring`, and `probe` to arrays of Wrangler service bindings. `resourceBindings` maps component keys (`api`, `statusApi`, `monitoring`, `status`, `admin`, `probe`, and `gateway`) to Wrangler binding blocks. Supported blocks are `r2_buckets`, `kv_namespaces`, `hyperdrive`, `analytics_engine_datasets`, `durable_objects`, `queues`, and `send_email`. Queue configuration supports producers only. Use staging resource identifiers for these blocks. The D1 database, routes, Cron Triggers, Worker names, and internal service bindings remain controlled by the deployment script. Do not put credentials in this JSON. Store sensitive values as Worker secrets on each preprovisioned Worker.

The feature build runs in a separate job without deployment credentials. Deployment packages use a guard from the trusted deployment script and the feature gateway and source. The deployment job verifies that every branch migration matches either the same-named main migration or an approved feature migration hash, and appears in the staging D1 migration table. Migrations require a separate staging operator process. Deployment clears the prior rollback target before updating the inactive stack. It runs Wrangler dry-runs before uploads and switches the active target only after all uploads complete. If upload fails, the previous stack stays selected. Rolling back switches to the last completed build while its stack has not been reused.

For a reviewed feature migration that has already been applied to staging and is not yet present on `main`, the operator can add an `approvedMigrationHashes` object to `PREVIEW_STAGING_CONFIG`. Its keys are exact migration filenames and its values are lowercase SHA-256 hashes of the applied SQL bytes, for example `{"0018_feature.sql":"<64-character SHA-256>"}`. Use `shasum -a 256 <migration-file>` to calculate the hash. Confirm the applied file and its compatibility with all active staging builds before adding the approval. The workflow still requires the filename in the D1 migration ledger. An approval does not override a same-named file on `main`, and changing the feature file requires a new review and hash.

The staging database, approved endpoints, and scheduled probe are shared. Coordinate stateful test records with other users. The preview probe handles only on-demand tests and has no Cron Trigger. Use selector-specific test record names and disabled monitors when testing changes.

## Subscriber scheduling

Preview subscriber scheduling is opt-in. First apply the reviewed preview-subscriber migration to the shared staging database and verify its ledger entry. In `PREVIEW_STAGING_CONFIG`, set `subscriberSchedulingEnabled` to `true`. Review the complete feature implementation and its imports before approving a manifest mapping exactly `preview-subscriber-scheduler.ts`, `subscriber-delivery.ts`, `subscribers.ts`, `email-channel.ts`, `idempotency.ts`, and `index.ts` to their lowercase SHA-256 hashes under the feature branch's `apps/worker/src` directory. These hashes are a compatibility check, not a sandbox for feature code.

Approve a manifest for a specific release by adding it to `approvedSubscriberSchedulers` under that release's exact 40-character commit SHA. Alternatively, add it to the `approvedSubscriberSchedulerSourceManifests` array to reuse the approval across commits whose six files are byte-identical; changes to other files do not require a new manifest. Multiple release-specific and reusable manifests can coexist. Any missing, extra, or changed file hash requires a matching reviewed manifest. A branch without a matching manifest and scheduler contract version 2 deploys normally with subscriber readiness disabled and no subscriber cron; the workflow summary reports `subscriberScheduler`. Contract version 2 requires the dispatcher to invoke the trusted authorization callback immediately before each send.

The `api` resource bindings must include exactly one `SUBSCRIBER_EMAIL` send-email binding restricted to one approved sender and one approved recipient. Configure the matching `SUBSCRIBERS_READY`, `SUBSCRIBER_EMAIL_READY`, `SUBSCRIBER_EMAIL_FROM`, `SUBSCRIBER_EMAIL_DESTINATIONS`, and `SUBSCRIBER_PUBLIC_URL` values in `apiVars`. Do not use an unrestricted binding. Each reviewed stack's private subscriber Worker runs every minute, checks the current Flagship slot, target, release, and expiry, then checks a durable D1 fence before dispatch. It rechecks both the global switch and the selected route before each email send. Flagship updates propagate across the network, so a recent switch change may not be visible immediately; D1 fencing also guards slot changes. It does not run the probe or publish the shared fallback. Slot deployment and rollback update the fence before switching Flagship; release revokes it before clearing the slot. A failed switch can pause delivery until retried. The dispatcher scopes data to a hash of the lease selector and uses fenced claims. Because sending an email is external to the D1 transaction, an already-started send can finish during a slot switch; wait for in-flight sends to finish before switching if strict cutover is required.

Open a preview enrollment confirmation link in a browser using that slot's selector through the preview launcher. Opening it in an ordinary baseline browser routes to the baseline and cannot confirm the preview subscription.

Release and expiry do not delete preview subscription data. For intentional cleanup, identify the old lease selector from its protected deployment record and calculate its SHA-256 locally. Confirm that the scope is no longer in `preview_subscriber_leases`, that no delivery for that scope is `sending`, and that its data is no longer needed. Then remove only rows matching that exact scope from `preview_subscriber_deliveries`, `preview_subscribers`, and `preview_subscription_settings`, in that order. Do not remove other scopes or baseline subscriber tables. Coordinate cleanup with the slot owner; pending deliveries will be discarded by this deletion.

## Branch preview controller prerequisites

Branch automation remains disabled until the repository variable `PREVIEW_AUTO_ENABLED` is set to `true`. The implementation requires a dedicated D1 control database with `.github/actions/branch-previews/src/release-inventory.sql` applied, a private dispatcher bound to the authenticated baseline gateway, a Flagship app, and Cloudflare permissions to create and manage the branch Workers, schema D1 databases and flags. The current slot-scoped token does not necessarily grant these permissions. A protected GitHub environment must restrict the deployment job to trusted main-branch controller code.

Subscriber testing in an automatic schema preview is a separate, explicit opt-in. The protected `PREVIEW_SCHEMA_SUBSCRIBER_CONFIG` secret is independent of the existing preview settings: set `enabled`, the exact `branch` and `release`, a millisecond `expiresAt` no more than 48 hours away, the one approved `sender`, `recipient` and staging `publicUrl`, the six-file `approvedSourceManifest`, `approvedArtifactHashes` for the built `api` and `subscriber` modules, and `approvedMigrationHashes` for the complete migration set. The trusted controller checks every hash and deploys the private scheduler only for that schema release. Dev, Stage and all other branches keep subscriber readiness disabled. After expiry, delivery and enrollment fail closed; to renew, make a new branch commit, review its complete source, built modules and migrations, and supply a new approval before redeploying. Keep the existing `PREVIEW_BRANCH_CONFIG` and unrelated secrets intact.

Each schema release has a distinct D1 database. The controller revokes the old release's durable subscriber lease before switching routes and creates a bounded lease for the candidate; retirement revokes leases before disabling the route. An expired approval or a new release without matching approval still deploys, with subscriber readiness disabled and the old lease revoked. Both confirmation sends and scheduled sends recheck the branch route and lease immediately before calling the provider. A provider call already in progress cannot be recalled. Email bindings permit only the approved sender and recipient. Subscription and fixture data reside in the schema preview's dedicated database, rather than shared staging.

Changing or removing `PREVIEW_SCHEMA_SUBSCRIBER_CONFIG` alone does not revoke an already deployed release. For runtime revocation, first delete the matching release's lease after verifying the owned schema database, scope and release, then clear the branch-specific Flagship route. The global preview switch can also stop preview routing, but affects every preview. Flagship changes propagate across the network; the database lease is the durable fence, and an email call already in progress can still finish. Reconcile the branch before restoring its route.

Store the branch controller's Cloudflare credential as the environment secret `CLOUDFLARE_BRANCH_PREVIEW_API_TOKEN`.

`PREVIEW_BRANCH_CONFIG` is an encrypted environment secret with `inventoryDatabaseId`, `dispatcherName`, `previewUrl`, `databases` and `environments` fields. `databases` contains `dev`, `stage`, and `prod` entries with `id` and, for Dev and Stage, `name`, plus optional `approvedMigrationHashes`. The `environments` object has `dev`, `stage`, and `schema` entries using the existing preview settings such as `accessTeamDomain`, `accessAud`, `endpoints`, and optional resource bindings. Database IDs in branch settings are selected by the controller, not by the feature branch.

`PREVIEW_WORKER_SECRETS` is an encrypted environment secret with common `verificationSecret` (at least 32 characters), `accessHeaders` (credentials accepted by the protected preview URL), and `environments` objects. `environments` must contain `dev`, `stage`, and `schema`, each with a `workers` object. Every `workers` object must explicitly contain `gateway`, `api`, `statusApi`, `monitoring`, `status`, `admin`, and `probe` objects mapping secret names to values. Use `{}` for a component without secrets and omit an unavailable key. Only the Worker secrets for the branch's selected environment are installed; no common Worker-secret fallback is used. Configure the staging Vault key only under `stage`, and use separate keys or omit them under `dev` and `schema`. Branch Workers receive these secrets and execute branch code, so choose credentials and branch access with that exposure in mind. The dispatcher verification secret is installed using Wrangler's standard input.

Deploy activation and cleanup require integration validation before rollout. Automatic deployment and reconciliation are controlled separately by `PREVIEW_AUTO_ENABLED` and `PREVIEW_RECONCILE_ENABLED`. Reconciliation inspects failed candidates and records owned resources before cleanup. The existing manually managed staging slots continue to use their own workflow.

## Isolated branch fixtures

The isolated fixture profile is an explicit protected-environment opt-in for reviewed feature commits. Store `PREVIEW_ISOLATED_FIXTURE_CONFIG` as an encrypted environment secret containing `inventoryDatabaseName`, `mail` (`from` and `to`, restricted to previously approved addresses), and `branches`. Each `branches` key is a complete ref such as `refs/heads/schema/example`, and its value includes the exact reviewed `sha`, boolean `cas`, `probe`, and `subscriber` capabilities, an `expiresAt` timestamp no more than 48 hours in the future, and approved hashes for every Worker, asset tree, and migration in `artifacts`. Generate and review those hashes from the exact GitHub build artifact using `describeFixtureArtifact`; do not rely on a feature-supplied approval. A changed commit or expired approval deploys with fixture privileges disabled, on a separate isolated database. Store an independent random 32-byte key as 64 hexadecimal characters in the separate environment secret `PREVIEW_ISOLATED_FIXTURE_ROOT`. Preserve this root for the lifetime of existing releases: the controller derives a distinct Vault and scheduler key for each release, and rotating it prevents existing releases from reading their Vault data.

An opted-in release uses its own migration-tested D1 even for `feat/`, `fix/`, or `stage/` refs. Its catalog points only to the private synthetic receiver. CAS requires the feature source to contain the CAS Worker, and subscriber delivery requires the reviewed scheduler contract. The trusted mailer allows only the configured sender and recipient, fixed templates, and at most four messages per selector per rolling hour. The private scheduler and mailer use controller-owned execution fences; only the fence Worker can access the inventory database. A release change or deletion drains outstanding work before switching its flag. If a Worker dies while holding a lease, the controller stops rather than automatically taking it over; inspect and recover the lease before retrying. Deleting a branch still follows the existing one-hour resource drain.

Fixture-capable action and reusable workflow references must be published and pinned in both layers before enabling the profile. Cron propagation may take up to 15 minutes; deployment success alone does not demonstrate a scheduled run. Ordinary previews remain subject to their original shared-database rules when not opted in.
