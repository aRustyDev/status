# Staging preview operations

The `Staging preview` workflow on `main` supports `deploy`, `list`, `rollback`, and `release` for slots 1–6. Deploy an existing same-repository branch and select a slot. The workflow summary gives the selector for `X-Status-Preview` and its commit. Slots are leased for 48 hours from a successful deployment, and only the owning branch can update, roll back, or release an active slot. After expiration a new branch can claim it. Use the browser launcher to inject the selector on staging requests.

The routing switch `status-preview-enabled` must be enabled in Flagship. Provision `status-preview-slot-1` through `status-preview-slot-6` as JSON flags with a `current` variation whose initial value is `{}` and default variation `current`. Each slot has two preprovisioned stacks named `status-preview-<slot>-<a|b>-<component>`. Components are `gateway`, `operations`, `status-api`, `monitoring-api`, `status-ui`, `admin-ui`, and `probe`. A reviewed subscriber-capable branch additionally deploys a private `subscriber` Worker per stack. Configure the main gateway with a service binding to each stack gateway. Provision staging secrets on the corresponding preview Workers before use. Probe schedules must remain empty.

Create a GitHub Actions environment `staging-preview`, restricted to `main`, with these values:

- Variables `FLAGSHIP_APP_ID` and `CLOUDFLARE_ACCOUNT_ID`.
- Secret `CLOUDFLARE_PREVIEW_API_TOKEN` scoped to editing only preview Workers, reading the staging D1 migration table, writing the staging Flagship app, and, when subscriber scheduling is enabled, writing the staging D1 scheduler fence.
- Secret `PREVIEW_STAGING_CONFIG` containing JSON with string fields `d1DatabaseId`, `d1DatabaseName`, `accessTeamDomain`, `accessAud`, and `endpoints`. Optional fields `uiMode`, `apiVars`, `statusApiVars`, `monitoringVars`, `probeVars`, `vpcServices`, `extraServices`, and `resourceBindings` carry the relevant staging configuration. `extraServices` maps `api`, `statusApi`, `monitoring`, and `probe` to arrays of Wrangler service bindings. `resourceBindings` maps component keys (`api`, `statusApi`, `monitoring`, `status`, `admin`, `probe`, and `gateway`) to Wrangler binding blocks. Supported blocks are `r2_buckets`, `kv_namespaces`, `hyperdrive`, `analytics_engine_datasets`, `durable_objects`, `queues`, and `send_email`. Queue configuration supports producers only. Use staging resource identifiers for these blocks. The D1 database, routes, Cron Triggers, Worker names, and internal service bindings remain controlled by the deployment script. Do not put credentials in this JSON. Store sensitive values as Worker secrets on each preprovisioned Worker.

The feature build runs in a separate job without deployment credentials. Deployment packages use a guard from the trusted deployment script and the feature gateway and source. The deployment job verifies that every branch migration matches either the same-named main migration or an approved feature migration hash, and appears in the staging D1 migration table. Migrations require a separate staging operator process. Deployment clears the prior rollback target before updating the inactive stack. It runs Wrangler dry-runs before uploads and switches the active target only after all uploads complete. If upload fails, the previous stack stays selected. Rolling back switches to the last completed build while its stack has not been reused.

For a reviewed feature migration that has already been applied to staging and is not yet present on `main`, the operator can add an `approvedMigrationHashes` object to `PREVIEW_STAGING_CONFIG`. Its keys are exact migration filenames and its values are lowercase SHA-256 hashes of the applied SQL bytes, for example `{"0018_feature.sql":"<64-character SHA-256>"}`. Use `shasum -a 256 <migration-file>` to calculate the hash. Confirm the applied file and its compatibility with all active staging builds before adding the approval. The workflow still requires the filename in the D1 migration ledger. An approval does not override a same-named file on `main`, and changing the feature file requires a new review and hash.

The staging database, approved endpoints, and scheduled probe are shared. Coordinate stateful test records with other users. The preview probe handles only on-demand tests and has no Cron Trigger. Use selector-specific test record names and disabled monitors when testing changes.

## Subscriber scheduling

Preview subscriber scheduling is opt-in. First apply the reviewed preview-subscriber migration to the shared staging database and verify its ledger entry. In `PREVIEW_STAGING_CONFIG`, set `subscriberSchedulingEnabled` to `true` and add an `approvedSubscriberSchedulers` object. Each key is an approved feature release's exact 40-character commit SHA; its value maps each of `preview-subscriber-scheduler.ts`, `subscriber-delivery.ts`, `subscribers.ts`, `email-channel.ts`, `idempotency.ts`, and `index.ts` to the lowercase SHA-256 of that file under the feature branch's `apps/worker/src` directory. Multiple releases can be approved at once. Review the complete feature implementation and its imports before approving the hashes; these hashes are a compatibility check, not a sandbox for feature code. New code revisions need renewed review and hashes. A branch without every matching hash deploys normally with subscriber readiness disabled and no subscriber cron; the workflow summary reports `subscriberScheduler`.

The `api` resource bindings must include exactly one `SUBSCRIBER_EMAIL` send-email binding restricted to one approved sender and one approved recipient. Configure the matching `SUBSCRIBERS_READY`, `SUBSCRIBER_EMAIL_READY`, `SUBSCRIBER_EMAIL_FROM`, `SUBSCRIBER_EMAIL_DESTINATIONS`, and `SUBSCRIBER_PUBLIC_URL` values in `apiVars`. Do not use an unrestricted binding. Each reviewed stack's private subscriber Worker runs every minute, checks the current Flagship slot, target, release, and expiry, then checks a durable D1 fence before dispatch. It does not run the probe or publish the shared fallback. Slot deployment and rollback update the fence before switching Flagship; release revokes it before clearing the slot. A failed switch can pause delivery until retried. The dispatcher scopes data to a hash of the lease selector and uses fenced claims. Because sending an email is external to the D1 transaction, an already-started send can finish during a slot switch; wait for in-flight sends to finish before switching if strict cutover is required.

Open a preview enrollment confirmation link in a browser using that slot's selector through the preview launcher. Opening it in an ordinary baseline browser routes to the baseline and cannot confirm the preview subscription.

Release and expiry do not delete preview subscription data. For intentional cleanup, identify the old lease selector from its protected deployment record and calculate its SHA-256 locally. Confirm that the scope is no longer in `preview_subscriber_leases`, that no delivery for that scope is `sending`, and that its data is no longer needed. Then remove only rows matching that exact scope from `preview_subscriber_deliveries`, `preview_subscribers`, and `preview_subscription_settings`, in that order. Do not remove other scopes or baseline subscriber tables. Coordinate cleanup with the slot owner; pending deliveries will be discarded by this deletion.
