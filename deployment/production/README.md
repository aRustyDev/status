# Private production deployment templates

These are incomplete examples, not deployable production configuration. Copy them into an owner-only directory and replace every `REPLACE_...` value after independently verifying the target account, database, Access application, private Gatus service, bucket, and Worker names. Use consistent names for every service reference. Because Wrangler resolves `main`, asset, and migration paths relative to the configuration file, replace those paths with absolute paths to the private worktree when moving a copy outside this directory. Never put credentials, private endpoints, or live identifiers into these tracked examples.

Suggested names are `status-operations-production`, `status-status-api-production`, `status-monitoring-api-production`, `status-ui-production`, `status-admin-ui-production`, `status-probe-production`, `status-gateway-production`, `status-fallback-production`, and `status-private-bridge-production`. Worker preview and workers.dev endpoints are disabled and no public routes are specified. The bridge is invoked by a separately managed, narrowly scoped Gateway Forward rule; `.woven` is not a public Worker custom domain. Do not alter the existing private hostname route, Access app, or shared Gateway policies during preparation.

The operations, status, and monitoring APIs bind the same Gatus VPC service and production D1. `GATUS_REQUIRED=true` deliberately fails closed when no reviewed catalog exists. Point the VPC service to the separately verified private Gatus origin, not to the Forward-intercepted frontend; exclude that traffic from Forward and test it. The probe remains unscheduled with an empty approved endpoint registry. Backups, alerts, actions, monitor authentication and custom request readiness are disabled until their individual dependencies and rollout gates are verified. Do not reuse staging's endpoints, secrets, resources, or policy audience.

Build `@bsp/shared`, `@bsp/board`, `@bsp/status`, `@bsp/admin`, and the fallback status build (`BSP_FALLBACK_BUILD=true`). Pin the candidate revision and independently verify the existing production D1 identity and migration state. Take a Time Travel bookmark and apply pending migrations only after the documented drain and compatibility checks. Provision a reviewed Gatus catalog with `scripts/gatus-catalog`; the tool's remote and production safeguards still apply.

Before changing production, use separate disposable resources to rehearse the exact artifact and configuration pattern, including private Access login and expiry, unauthorized and forged requests, API role checks, Gatus inventory and failure, fallback serving, protocol bypasses, and rollback. A Wrangler `--dry-run` checks packaging only. Do not infer correct Access or Gateway behavior from the template or a dry run.

Deploy the probe and APIs, status and admin UIs, gateway, fallback, and bridge as private Workers. The operations template intentionally starts with `FALLBACK_READY=false` and no cron; after its bucket binding is verified, enable readiness and the one-minute cron in the environment-specific configuration and redeploy operations. The fallback Worker retains no public route; the Gateway Forward bridge reaches it through a service binding. Bootstrap the first administrator by verifying the Access issuer, subject, email and D1 row before its narrowly scoped role update.

Only after the isolated rehearsal and the Gatus origin and dependent consumers are verified should the managed production Forward and Access configuration be changed. Record exact prior route, app, policy and Worker versions. To roll back, disable the Forward rule before removing its Worker, restore the previous private routing and Access behavior without changing shared policies, and verify Gatus reader access, checks, alerts and dead-man health. Keep the Gatus VM and its SQLite history intact.
