# Extract reusable branch previews for GitHub Actions

Package the branch preview controller from Status so a second repository can deploy and retire feature branches through the same workflows. Use the merge of PR #100, `622bc92be807ec59ec907fd6f3b6515a78239459`, as the compatibility baseline. The release gate is two repositories serving distinct commits from identically named branches, followed by deletion of one preview while the other continues serving traffic. [Original implementation](https://github.com/aRustyDev/status/pull/95) · [Baseline source](https://github.com/aRustyDev/status/tree/622bc92be807ec59ec907fd6f3b6515a78239459)

## Consumer contract

Each repository supplies a small caller workflow and a `.github/previews.yml` manifest on its protected default branch. The manifest identifies the CI workflow, branch-to-environment mapping, build outputs, components, migration paths, schema fixture, and application smoke check. The repository's protected preview environment holds deployment credentials and approved resource bindings.

- **Deploy.** Call `deploy.yml` after successful CI or by manual dispatch with `branch`, `sha`, and `config`. Verify the same-repository branch, successful CI, and exact remote SHA. Build the feature commit on a runner without deployment credentials. In a separate job, validate the artifact, deploy a private candidate, and recheck the branch head before activation. Probe the candidate before publishing its Flagship mapping, then confirm the expected SHA through the authenticated shared URL. Return `url`, `header_name`, `selector`, `sha`, and `environment`. Include a selector-aware browser-launch command in the run summary.
- **Reconcile.** Call `reconcile.yml` on branch deletion, on a schedule, or by manual dispatch. Recover interrupted releases, schedule eligible missing deployments, and retire resources after the drain. Give this job `actions: write` when it must redispatch CI or deployment. Deployment needs only read access to Actions and repository contents.
- **Package.** Ship the two reusable workflows and one versioned controller action. Reuse the public GitHub checkout, setup, and artifact actions. Run pinned Wrangler where the controller needs to record resource ownership between provider calls. Pin the controller action in the reusable workflows and pin the reusable workflow revision in each caller. Set the protected environment on the credentialed job inside the called workflow. [Existing workflow](../../.github/workflows/branch-previews.yml) · [GitHub reusable workflows](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows)

## Ownership and routing

The existing selector derives from the Git ref, so two repositories with `feat/login` would derive the same key. Each installation should own its dispatcher and inventory. Derive new installations' resource names and selectors from a stable installation namespace incorporating the GitHub repository ID. Apply that namespace to Workers, Flagship keys, and schema databases. Reserve Status's existing namespace for compatibility and verify reads of existing inventory and active selectors before cutover. Serialize deployment and reconciliation for each dispatcher using the same non-preemptive concurrency group. Multiple branch releases can serve traffic while a routing update is queued. [Release identity](../../scripts/preview/release-contract.mjs) · [Inventory schema](../../scripts/preview/release-inventory.sql) · [Dispatcher updates](../../scripts/preview/release-activation.mjs)

V1 provides one authenticated preview URL per application. The header selects a branch at request time, and Flagship supplies its active release. Keep `X-Status-Preview` for Status. The first compute adapter uses ordinary Workers service bindings. Keep preparation, probing, route publication, and retirement behind interfaces that a future hosting adapter can implement. The application's gateway continues routing when the GitHub runner exits. [Current dispatcher](../../apps/gateway/preview-dispatcher.ts)

## Workstreams and worktrees

The proposed package repository is `aRustyDev/branch-previews`. Use `aRustyDev/status` as the compatibility consumer and a disposable `aRustyDev/branch-previews-fixture` as the independent consumer. Give each stream a sibling worktree under `~/repos/preview-worktrees/` on branch `codex/<worktree-name>` in the indicated repository.

| Stream | Repository / worktree | Owned deliverable | Dependencies |
| --- | --- | --- | --- |
| 1. Contract and compatibility | Package / `preview-contract` | Version the manifest, action interface, artifact layout, resource identity, inventory format, and provider interfaces. Capture sanitized Status inventory and routing fixtures. | Starts first |
| 2. Release controller | Package / `preview-core` | Extract CI and exact-ref verification, release generations, compare-and-swap, activation state, recovery, and retirement. Test duplicate events, stale commits, interrupted writes, and branch recreation. | 1 |
| 3. Compute and routing | Package / `preview-routing` | Generate private Worker stacks from the manifest. Own dispatcher bindings, Flagship writes, and signed candidate and active-route probes. Port the propagation and retry tests. | 1 |
| 4. Database lifecycle | Package / `preview-database` | Extract shared migration checks, isolated clean-install and seeded-upgrade tests, and deletion by recorded database identity. Accept the consumer's schema fixture. | 1 |
| 5. GitHub Actions packaging | Package / `preview-workflows` | Own `action.yml`, both reusable workflows, runner and artifact boundaries, release packaging, and consumer documentation. Develop against a stub controller. | 1 to draft. Integrate 2–4 before release |
| 6. Status adoption | Status / `preview-status-consumer` | Declare the seven Workers, bindings, assets, and schema fixture in the manifest. Preserve launcher and fallback behavior, inventory, selectors, and manual slots. Prepare a reversible caller change. | 1 to draft. Pin the release candidate for cutover |
| 7. Independent consumer | Fixture / `preview-fixture-consumer` | Build one Worker with a different CI workflow name, source layout, and migration directory. Use its own preview resources and credentials. Expose an application marker and commit. | 1 to draft. Pin the release candidate for deployment |
| 8. Integration and release | Package / `preview-release` | Integrate the package, publish an immutable release candidate, collect evidence from both consumers, and release the tested revision as v1. | 2–5 for the candidate. 6–7 and the live gates for v1 |

After stream 1 lands, streams 2–7 can run in parallel. Stream 8 assembles the candidate from 2–5. Deploy the fixture first to detect packaging or permissions problems, then switch Status and run both consumers together.

## Two-repository verification

Pin both caller workflows to the same release candidate. Capture the initial active selectors, dispatcher bindings, deployment identifiers, schema database identifiers, and inventory revisions. Use application-specific markers and commit SHAs to distinguish working routes from a cached response or shared fallback.

| Gate | Procedure | Evidence required |
| --- | --- | --- |
| 1. Simultaneous deployment | Push `feat/preview-e2e` with different commits to both repositories. Use each application's authenticated URL with its selector, without a selector, and with the other installation's selector. | Each selected response carries the expected commit header and application marker. Each unselected request serves its baseline. The other installation's selector cannot select a release. |
| 2. Branch updates and trust | Push two rapid updates to Status, replay a completed deployment, and submit failed-CI and wrong-SHA candidates. Keep probing the fixture. | A superseded candidate cannot activate. A duplicate deployment creates no resources. Rejected candidates receive no traffic, and the fixture continues serving its original commit. |
| 3. Database policy | Exercise `feat/*` and `fix/*` against shared Dev, `stage/*` against shared Stage, and identically named `schema/*` branches in both repositories. Include an unapplied shared migration. Run both fresh-install and seeded-upgrade tests for schema releases. | The unapplied migration blocks the shared preview. Each schema preview serves from its own upgrade database with its expected fixture data. The temporary clean-install database is removed. Binding and operation records show Prod received no preview binding or write. |
| 4. Pilot regressions | Launch a branch selector in the browser. Exercise a failing preview on a fallback path. Use adapter tests to inject transient candidate failures, delayed flag propagation, and permanent failure. | The launcher sends the selector. Requests carrying the header reach the gateway, including invalid selectors, and a failed preview never displays the shared Stage snapshot. Candidate verification retries for up to 60 seconds before publication. Active-route verification allows up to 120 seconds and requires the expected SHA. |
| 5. Deletion, drain, and recovery | Delete a schema branch in one repository while its same-named counterpart remains live. Reconcile immediately and again after the real one-hour drain. Separately test recreation during drain and GitHub responses of 403, 422, and 5xx. | Routing clears before resource deletion. After the drain, the deleted preview's dispatcher binding, owned Workers, and owned schema database are gone. Inventory records retirement. The sibling preview still serves its SHA and retains its data. Recreating a branch or encountering an ambiguous lookup prevents destructive cleanup. |

Carry the five pilot fixes into the appropriate owner above. Browser selector acceptance and shared fallback bypass belong in the Status integration. Candidate retry and active-route propagation belong in the routing adapter. The controller must identify a deleted branch through an exact Git ref lookup and distinguish a missing ref from API failures. [Browser selectors, #96](https://github.com/aRustyDev/status/pull/96) · [Active-route propagation, #97](https://github.com/aRustyDev/status/pull/97) · [Fallback isolation, #98](https://github.com/aRustyDev/status/pull/98) · [Candidate retries, #99](https://github.com/aRustyDev/status/pull/99) · [Deleted refs, #100](https://github.com/aRustyDev/status/pull/100)

## Status cutover and v1 release

1. Pause the old automatic writer and let its current run finish. Record active selectors and inventory revisions. Confirm the candidate can read the existing records and resolve existing selectors.
2. Enable the pinned caller and run the gates above. Keep the previous workflow available for rollback. To revert, pause and drain the new writer, verify inventory compatibility, then re-enable the previous writer. Only one controller may write to the Status dispatcher at a time.
3. Publish v1 from the tested revision after the live drain completes. Attach both repositories' workflow run links, expected and observed commit headers, and before-and-after resource inventories to the release evidence. Verify the surviving preview before removing the remaining pilot branches and reconciling their resources.
