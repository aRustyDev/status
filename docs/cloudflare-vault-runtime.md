# Cloudflare Vault runtime contract

Vault secret values are encrypted in D1 and are never returned by the management API. The in-process runtime resolver is available only to Workers that have both the D1 binding and the environment's `VAULT_ENCRYPTION_KEY`. Those Workers are trusted with the key; anyone able to deploy code to one of them or read its runtime secrets can access the environment's Vault data. Give those permissions only to trusted operators. Keep the same key in the recovery store and alongside backup recovery procedures; do not put it in repository configuration, queues, logs, or audit details.

The resolver accepts a persisted integration ID and its version, not a caller-supplied vault reference. It reads the current reference for that integration, checks the database-bound key verifier, secret type and vault membership, then authenticates the ciphertext with AES-GCM and the original associated data. Resolution failure returns a generic unavailable result without exposing provider errors or values. Rotation is observed on the next lookup. A deleted, missing, tampered, wrongly typed or inaccessible secret fails closed. Before each outbound attempt, the runtime checks the saved integration and approved destination along with the resolved secret identity, version and nonce. A change visible to that check fails the attempt; a later lookup can use a replacement. This is a pre-send snapshot, not instantaneous revocation: a secret, integration or destination change after the final check can race a request already in flight. For strict revocation, stop new affected probes, dispatches and manual tests, and drain in-flight requests before making the change. Follow the drain procedure in [Cloudflare deployment](cloudflare-deployment.md), including trigger propagation and invocation time. Credentials must not enter jobs, outbox entries, test results, HTTP API responses, audit details or logs.

The supported callers are the scheduled HTTP probe, the webhook delivery runtime and the narrow HTTP action runner. A saved Basic-auth monitor resolves only its saved check ID and configuration version; a webhook or action resolves only its saved integration ID and version. Outbox records contain IDs, versions and execution state, not credentials. Never expose a general-purpose resolve endpoint to a browser or accept arbitrary reference IDs in a runtime job. An administrator who can configure an integration and an approved destination can cause the credential associated with that integration to be sent to that destination; grant those configuration permissions accordingly.

The Cloudflare action runner supports only the explicitly configured webhook action and monitor status transitions. Each saved action has its own ID, version, approved HTTPS target, monitor associations and Vault reference. It claims an event before execution and never retries an outbound action attempt. A claim deferred before sending, such as during maintenance or a credential fault, can return to pending; a crash or ambiguous response is recorded as uncertain for operator review. It does not implement the full upstream Actions feature, so unsupported action types, templates and monitor-editor controls must remain unavailable. Extend this path with its own scoped resolution and end-to-end tests before enabling any additional action type.

When a monitor credential cannot be resolved or its authentication configuration cannot be verified, the check records down and emits the fixed `probe_credential_unavailable` diagnostic with its check ID. The fault observation does not enqueue notifications or actions and does not change their last valid transition baseline. Pending work waits while the credential fault persists. A subsequent valid observation is compared with that baseline: an actual change can trigger automation, while an unchanged status does not generate a false recovery. If no trustworthy baseline exists, the valid observation establishes one; an initial unhealthy observation can notify a channel. See [Cloudflare notification channels](cloudflare-notifications.md) and [Cloudflare actions](cloudflare-actions.md) for the delivery semantics.

Basic authentication uses the UTF-8 encoding of `username:password`; the username must not contain a colon. The complete Base64-encoded Authorization header value, including `Basic `, must not exceed 8,192 characters. An oversized credential is treated as unavailable without contacting the target or generating an automation transition.
