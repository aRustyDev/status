# Cloudflare actions

The Cloudflare profile supports one action provider: a fixed deployment-approved HTTPS POST with a Bearer token from a local Vault Secure Value. Administrators can assign local monitors from the action editor and select up, degraded, down, or any status change. The monitor's Actions panel can instead configure individual down and recovery links, including delay and cooldown; these monitor-specific settings override that action's global trigger for the monitor. Links may be saved before a monitor has a check, but run only after a check is configured. The first result establishes a baseline and does not run an action. Gatus-managed monitors, arbitrary request templates, direct credentials, manual test runs and other action providers remain unavailable. Action names are visible metadata; do not put credentials there.

After upgrading, refresh any previously open admin tabs before editing actions. Older pages lack the monitor identity and version snapshots required to save; the API rejects their saves with a refresh message rather than risking an action on the wrong monitor.

`ACTION_ENDPOINTS` is a separate JSON allowlist in the same format as `ENDPOINTS`. Every target must be HTTPS, including bound services. An action stores the selected target's fingerprint; attempts that observe a change to its URL, binding, service ID or revision fail closed until an administrator re-saves the action. Review every target carefully: an action may change an external system and the target receives the Bearer token. Do not embed credentials in the target URL. Tokens must be at most 4096 characters, use only letters, digits, hyphen, dot, underscore, tilde, plus and slash, and may have trailing equals signs. Whitespace and other characters fail closed.

Before applying `0017_monitor_action_links.sql`, turn off `ACTIONS_READY` for both Workers and drain the probe as described in [Cloudflare deployment](cloudflare-deployment.md). An older probe does not understand per-monitor policies, delay or cooldown and must not run with Actions enabled after the new UI makes those settings available. Apply the migration, then deploy the new probe with the Vault key, `ACTION_ENDPOINTS` and required bindings, then deploy the operations Worker with the same key, equivalent allowlist and bindings. Verify both Workers' endpoint IDs, fingerprints, key and bindings. Set `ACTIONS_READY=true` in **both** Workers only after this verification, deploy both again, and then deploy the admin UI. Repeat the verification whenever either Worker's configuration changes. A missing flag, invalid allowlist or unavailable Vault key keeps the feature unavailable. Removing readiness stops dispatching pending jobs after the configuration takes effect but does not cancel in-flight requests; pending jobs normally expire one hour after they become due, except those held across a maintenance window.

An accepted monitor status transition and its action job are committed in one D1 transaction. The job contains only identifiers and state, never the credential or destination URL. If the outbox table is missing or broken while `ACTIONS_READY=true`, that transaction rolls back the check result as well; migrate and verify before enabling readiness, and disable the flag if the outbox is unavailable. Before executing, the probe claims the job, checks the saved action and monitor versions and approved destination fingerprint, then resolves the Vault value. Requests use POST, a five-second timeout, no redirect following and a stable idempotency key. The JSON body contains the event type, check ID, status and scheduled time, which the destination should treat as operational metadata.

Each job is sent at most once: the runtime never automatically retries an action after its outbound attempt. A claim deferred before sending can return to pending. If a worker crashes before sending, the action may not run; if a request times out, returns a non-success status or the worker crashes after sending, the result is marked uncertain and the external system may already have acted. Inspect the destination before taking further action. The idempotency key provides an additional guard for receivers that support it. Runs have generic completed, unavailable or uncertain states; response bodies and errors are not stored or returned. Pending jobs normally expire one hour after they become due; jobs held across a maintenance window are exempt from that timer. Terminal records are retained for approximately 24 hours, and cleanup is bounded. Up to 20 actions are attempted per scheduled tick.

For a down or recovery link, the delay is measured from the time the accepted transition is processed, in whole minutes from 0 to 10,080. A scheduled action is discarded when a later accepted transition supersedes it, including recovery before a delayed down action becomes due. Editing or removing the specific policy also invalidates its pending job; unchanged policies retain their pending jobs. Dispatch occurs on the probe schedule, so a due action may run later than its configured delay.

Cooldown is per monitor, action and trigger status. A claim reserves the cooldown atomically, preventing concurrent duplicate sends; a pre-send rejection or deferral releases that reservation. A completed or uncertain attempt consumes it, because an uncertain request may already have reached the destination. Failures are reported as unavailable or uncertain, and are not automatically retried after a request might have been sent. Existing global degraded-only associations remain in effect when the monitor panel saves unrelated links; remove those associations in the action editor.

Maintenance suppresses transitions for affected checks. A job queued before a window waits for a valid post-window observation, and a newer transition supersedes an older pending job even when the status later returns to the same value. Dispatch checks maintenance again before sending, but that check is a snapshot: a window activated or changed after the final check can race an in-flight action. For strict suppression, stop new dispatches and drain in-flight requests before activating or changing the window; follow the probe drain procedure in [Cloudflare deployment](cloudflare-deployment.md), including trigger propagation and invocation time. Credential-unavailable observations also hold pending jobs until a valid observation. Migration `0010_notification_transition_state.sql` marks legacy pending actions unavailable and legacy executing actions uncertain; inspect the destination before deciding how to handle an uncertain action.
