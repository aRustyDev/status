# Cloudflare actions

The Cloudflare profile supports one action provider: a fixed deployment-approved HTTPS POST with a Bearer token from a local Vault Secure Value. Administrators assign local monitors with checks and select the transition that triggers an action: up, degraded, down, or any status change. The first result establishes a baseline and does not run an action. Gatus-managed monitors, arbitrary request templates, direct credentials, manual test runs and other action providers remain unavailable. Action names are visible metadata; do not put credentials there.

`ACTION_ENDPOINTS` is a separate JSON allowlist in the same format as `ENDPOINTS`. Every target must be HTTPS, including bound services. An action stores the selected target's fingerprint; changing its URL, binding, service ID or revision stops execution until an administrator re-saves the action. Review every target carefully: an action may change an external system and the target receives the Bearer token. Do not embed credentials in the target URL. Tokens must be at most 4096 characters, use only letters, digits, hyphen, dot, underscore, tilde, plus and slash, and may have trailing equals signs. Whitespace and other characters fail closed.

Apply the migrations, deploy the probe with the Vault key, `ACTION_ENDPOINTS` and required bindings, then deploy the operations Worker with the same key, equivalent allowlist and bindings. Verify both Workers' endpoint IDs, fingerprints, key and bindings. Set `ACTIONS_READY=true` in **both** Workers only after this verification, deploy both again, and then deploy the admin UI. Repeat the verification whenever either Worker's configuration changes. A missing flag, invalid allowlist or unavailable Vault key keeps the feature unavailable. Removing readiness stops pending work; events that remain pending for more than one hour fail without execution.

An accepted monitor status transition and its action job are committed in one D1 transaction. The job contains only identifiers and state, never the credential or destination URL. If the outbox table is missing or broken while `ACTIONS_READY=true`, that transaction rolls back the check result as well; migrate and verify before enabling readiness, and disable the flag if the outbox is unavailable. Before executing, the probe claims the job permanently, checks the saved action and monitor versions and approved destination fingerprint, then resolves the Vault value. Requests use POST, a five-second timeout, no redirect following and a stable idempotency key. The JSON body contains the event type, check ID, status and scheduled time, which the destination should treat as operational metadata.

Each job is attempted at most once: the runtime never automatically retries a claimed action. If a worker crashes before sending, the action may not run; if a request times out, returns a non-success status or the worker crashes after sending, the result is marked uncertain and the external system may already have acted. Inspect the destination before taking further action. The idempotency key provides an additional guard for receivers that support it. Runs have generic completed, unavailable or uncertain states; response bodies and errors are not stored or returned. Pending jobs expire after one hour, terminal records are retained for approximately 24 hours, and cleanup is bounded. Up to 20 actions are attempted per scheduled tick.
