# Branch preview operations

## Branch preview controller prerequisites

Branch automation remains disabled until the repository variable `PREVIEW_AUTO_ENABLED` is set to `true`. The implementation requires a dedicated D1 control database with `.github/actions/branch-previews/src/release-inventory.sql` applied, a private dispatcher bound to the authenticated baseline gateway, a Flagship app, and Cloudflare permissions to create and manage the branch Workers, schema D1 databases and flags. The current slot-scoped token does not necessarily grant these permissions. A protected GitHub environment must restrict the deployment job to trusted main-branch controller code.

Subscriber testing in an automatic schema preview is a separate, explicit opt-in. The protected `PREVIEW_SCHEMA_SUBSCRIBER_CONFIG` secret is independent of the existing preview settings: set `enabled`, the exact `branch` and `release`, a millisecond `expiresAt` no more than 48 hours away, the one approved `sender`, `recipient` and staging `publicUrl`, the six-file `approvedSourceManifest`, `approvedArtifactHashes` for the built `api` and `subscriber` modules, and `approvedMigrationHashes` for the complete migration set. The trusted controller checks every hash and deploys the private scheduler only for that schema release. Dev, Stage and all other branches keep subscriber readiness disabled. After expiry, delivery and enrollment fail closed; to renew, make a new branch commit, review its complete source, built modules and migrations, and supply a new approval before redeploying. Keep the existing `PREVIEW_BRANCH_CONFIG` and unrelated secrets intact.

Each schema release has a distinct D1 database. The controller revokes the old release's durable subscriber lease before switching routes and creates a bounded lease for the candidate; retirement revokes leases before disabling the route. An expired approval or a new release without matching approval still deploys, with subscriber readiness disabled and the old lease revoked. Both confirmation sends and scheduled sends recheck the branch route and lease immediately before calling the provider. A provider call already in progress cannot be recalled. Email bindings permit only the approved sender and recipient. Subscription and fixture data reside in the schema preview's dedicated database, rather than shared staging.

Changing or removing `PREVIEW_SCHEMA_SUBSCRIBER_CONFIG` alone does not revoke an already deployed release. For runtime revocation, first delete the matching release's lease after verifying the owned schema database, scope and release, then clear the branch-specific Flagship route. The global preview switch can also stop preview routing, but affects every preview. Flagship changes propagate across the network; the database lease is the durable fence, and an email call already in progress can still finish. Reconcile the branch before restoring its route.

Store the branch controller's Cloudflare credential as the environment secret `CLOUDFLARE_BRANCH_PREVIEW_API_TOKEN`.

`PREVIEW_BRANCH_CONFIG` is an encrypted environment secret with `inventoryDatabaseId`, `dispatcherName`, `previewUrl`, `databases` and `environments` fields. `databases` contains `dev`, `stage`, and `prod` entries with `id` and, for Dev and Stage, `name`, plus optional `approvedMigrationHashes`. The `environments` object has `dev`, `stage`, and `schema` entries using the existing preview settings such as `accessTeamDomain`, `accessAud`, `endpoints`, and optional resource bindings. Database IDs in branch settings are selected by the controller, not by the feature branch.

`PREVIEW_WORKER_SECRETS` is an encrypted environment secret with common `verificationSecret` (at least 32 characters), `accessHeaders` (credentials accepted by the protected preview URL), and `environments` objects. `environments` must contain `dev`, `stage`, and `schema`, each with a `workers` object. Every `workers` object must explicitly contain `gateway`, `api`, `statusApi`, `monitoring`, `status`, `admin`, and `probe` objects mapping secret names to values. Use `{}` for a component without secrets and omit an unavailable key. Only the Worker secrets for the branch's selected environment are installed; no common Worker-secret fallback is used. Configure the staging Vault key only under `stage`, and use separate keys or omit them under `dev` and `schema`. Branch Workers receive these secrets and execute branch code, so choose credentials and branch access with that exposure in mind. The dispatcher verification secret is installed using Wrangler's standard input.

Automatic deployment and reconciliation are controlled separately by `PREVIEW_AUTO_ENABLED` and `PREVIEW_RECONCILE_ENABLED`. Reconciliation inspects failed candidates and records owned resources before cleanup. The existing manually managed staging slots continue to use their own workflow.

## Isolated branch fixtures

The isolated fixture profile is an explicit protected-environment opt-in for reviewed feature commits. Store `PREVIEW_ISOLATED_FIXTURE_CONFIG` as an encrypted environment secret containing `inventoryDatabaseName`, `mail` (`from` and `to`, restricted to previously approved addresses), and `branches`. Each `branches` key is a complete ref such as `refs/heads/schema/example`, and its value includes the exact reviewed `sha`, boolean `cas`, `probe`, and `subscriber` capabilities, an `expiresAt` timestamp no more than 48 hours in the future, and approved hashes for every Worker, asset tree, and migration in `artifacts`. Generate and review those hashes from the exact GitHub build artifact using `describeFixtureArtifact`; do not rely on a feature-supplied approval. A changed commit or expired approval deploys with fixture privileges disabled, on a separate isolated database. Store an independent random 32-byte key as 64 hexadecimal characters in the separate environment secret `PREVIEW_ISOLATED_FIXTURE_ROOT`. Preserve this root for the lifetime of existing releases: the controller derives a distinct Vault and scheduler key for each release, and rotating it prevents existing releases from reading their Vault data.

An opted-in release uses its own migration-tested D1 even for `feat/`, `fix/`, or `stage/` refs. Its catalog points only to the private synthetic receiver. CAS requires the feature source to contain the CAS Worker, and subscriber delivery requires the reviewed scheduler contract. The trusted mailer allows only the configured sender and recipient, fixed templates, and at most four messages per selector per rolling hour. The private scheduler and mailer use controller-owned execution fences; only the fence Worker can access the inventory database. A release change or deletion drains outstanding work before switching its flag. If a Worker dies while holding a lease, the controller stops rather than automatically taking it over; inspect and recover the lease before retrying. Deleting a branch still follows the existing one-hour resource drain.

Fixture-capable action and reusable workflow references must be published and pinned in both layers before enabling the profile. Cron propagation may take up to 15 minutes; deployment success alone does not demonstrate a scheduled run. Ordinary previews remain subject to their original shared-database rules when not opted in.
