# Cloudflare notification channels

The Cloudflare profile supports one notification provider: an HTTPS webhook with a Bearer token from a local Vault Secure Value. Other providers, SMTP and upstream alert-hygiene policies are unavailable. Administrators create a channel, select a deployment-approved destination and assign local monitors with checks. Gatus-managed monitors are not assignable. A channel sends only when a known check result changes between up, degraded and down; its first result establishes a baseline. A saved channel can also send a test. The body contains the event type, check ID, status and scheduled time; it contains no credential. Recipients should treat monitor identifiers and status as operational metadata.

`CHANNEL_ENDPOINTS` is a JSON array in the same format as `ENDPOINTS`, but is a separate deployment-controlled allowlist for POST destinations. Every entry must use HTTPS, including service bindings. Each channel stores the selected endpoint's fingerprint; if its URL, binding, service ID or revision changes, delivery fails closed until an administrator re-saves the channel. Configure bindings explicitly and review each destination: a destination receives the Vault token and event metadata. Tokens must be at most 4096 characters, use only letters, digits, hyphen, dot, underscore, tilde, plus and slash, and may have trailing equals signs. Whitespace and other characters fail closed. Do not put credentials in channel names or endpoint URLs; names are visible metadata. The API returns destination IDs and names, never endpoint URLs, tokens, response headers or bodies.

To enable channels, apply migrations and deploy the new probe first with the Vault key, `CHANNEL_ENDPOINTS` and any destination bindings, then deploy the operations Worker with the same key and equivalent endpoint configuration and bindings. Verify the endpoint IDs, fingerprints and bindings in both deployed Workers and their connectivity. Only then set `CHANNELS_READY=true` in **both** Workers and deploy them, followed by the admin UI. This explicit readiness assertion is required in addition to a valid Vault key and at least one approved endpoint; if it is missing, channels remain disabled. Removing or changing the assertion stops queued delivery; it does not remove pending events. The operator must repeat this verification after either Worker's bindings, secrets or endpoint list change.

Events are written atomically with accepted check results to a D1 outbox containing identifiers and status, never resolved credentials or destination URLs. Dispatch resolves the current Vault value for the saved channel version immediately before sending, checks the channel and monitor versions and the destination fingerprint, sends with redirects disabled and a five-second timeout, and never records response bodies or exception messages. Secret rotation takes effect on the next attempt. Missing secrets, changed/deleted channels or monitor configurations, disabled channels and destination drift fail closed with a generic `unavailable` result. Failed requests retry on later scheduled ticks up to three attempts. Pending events expire after one hour, so sustained flapping or a backlog can cause them to fail rather than accumulate indefinitely. Leases prevent concurrent Workers from normally sending the same event together, but a crash after the receiver accepts and before the sender records success can cause duplicate delivery. Receivers should be idempotent. Terminal delivery records are retained for approximately 24 hours and pruned in batches of up to 500 per scheduled tick. Up to 20 deliveries are attempted per tick; monitor delivery status for capacity problems. Recent delivery states and generic error codes are visible to administrators; failed requests are not silently reported as successful.

The outbox insert shares the check-result transaction. This prevents alerts for a result that was not committed, but a missing or broken outbox table will roll back the check result while `CHANNELS_READY=true`. Apply and verify the migration before enabling readiness, and set the flag to false if the outbox is unavailable.
