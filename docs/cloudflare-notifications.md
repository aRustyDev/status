# Cloudflare notification channels

The Cloudflare profile supports deployment-approved email recipients through a Cloudflare Email Sending binding, and HTTPS webhooks with a Bearer token from a local Vault Secure Value. Other providers, SMTP and upstream alert-hygiene policies are unavailable. Administrators create a channel, select a deployment-approved destination and assign local monitors, including those that do not yet have a check. Alerts are emitted only for enabled checks. Gatus-managed monitors are not assignable. A channel sends only when a known check result changes between up, degraded and down; its first healthy result establishes a baseline; a new check’s first unhealthy result can notify. A saved channel can also send a test. The body contains the event type, check ID, status and scheduled time; it contains no credential. Recipients should treat monitor identifiers and status as operational metadata.

`CHANNEL_ENDPOINTS` is a JSON array in the same format as `ENDPOINTS`, but is a separate deployment-controlled allowlist for POST destinations. Every entry must use HTTPS, including service bindings. Each channel stores the selected endpoint's fingerprint; if its URL, binding, service ID or revision changes, delivery fails closed until an administrator re-saves the channel. Configure bindings explicitly and review each destination: a destination receives the Vault token and event metadata. Tokens must be at most 4096 characters, use only letters, digits, hyphen, dot, underscore, tilde, plus and slash, and may have trailing equals signs. Whitespace and other characters fail closed. Do not put credentials in channel names or endpoint URLs; names are visible metadata. The API returns destination IDs and names, never endpoint URLs, tokens, response headers or bodies.

Before applying the automation-state migration, stop and drain the old probe scheduler; the migration fails legacy pending jobs closed because their transition generation cannot be reconstructed. Apply migrations and deploy the new probe first with the Vault key, `CHANNEL_ENDPOINTS` and any destination bindings, then deploy the operations Worker with the same key and equivalent endpoint configuration and bindings. Verify the endpoint IDs, fingerprints and bindings in both deployed Workers and their connectivity. Only then set `CHANNELS_READY=true` in **both** Workers and deploy them, followed by the admin UI. This explicit readiness assertion is required in addition to a valid Vault key and at least one approved endpoint; if it is missing, channels remain disabled. Removing or changing the assertion stops queued delivery; it does not remove pending events. The operator must repeat this verification after either Worker's bindings, secrets or endpoint list change.

Events are written atomically with accepted check results to a D1 outbox containing identifiers and status, never resolved credentials or destination URLs. Dispatch resolves the current Vault value for the saved channel version immediately before sending, checks the channel and monitor versions and the destination fingerprint, sends with redirects disabled and a five-second timeout, and never records response bodies or exception messages. Secret rotation takes effect on the next attempt. Missing secrets, changed/deleted channels or monitor configurations, disabled channels and destination drift fail closed with a generic `unavailable` result. Webhook requests retry on later scheduled ticks up to three attempts, with a stable `Idempotency-Key`; receivers must deduplicate this key. Email sends are attempted at most once: an ambiguous failure or crash may lose an alert, rather than risk sending a duplicate. Pending events expire after one hour, so sustained flapping or a backlog can cause them to fail rather than accumulate indefinitely. Leases prevent concurrent Workers from normally sending the same event together, but a webhook receiver must honor the stable idempotency key to prevent duplicates after an ambiguous response. Email Sending does not provide equivalent receiver deduplication; an accepted message is not proof of inbox delivery. Terminal delivery records are retained for approximately 24 hours and pruned in batches of up to 500 per scheduled tick. Up to 20 deliveries are attempted per tick; monitor delivery status for capacity problems. Recent delivery states and generic error codes are visible to administrators; failed requests are not silently reported as successful.

The outbox insert shares the check-result transaction. This prevents alerts for a result that was not committed, but a missing or broken outbox table will roll back the check result while `CHANNELS_READY=true`. Apply and verify the migration before enabling readiness, and set the flag to false if the outbox is unavailable.

## Email channels and monitor Alerts

> [!WARNING]
> **Not released yet.** Email channels and monitor Alerts require a build from the `main` branch (see [Deployment](deployment.md)).

An administrator can select an approved email recipient from the Notifications page, then select that channel in a monitor's Alerts panel. Disabled channels can remain selected but send no alerts. A new check’s first unhealthy observation can alert; its first healthy observation establishes a baseline. Subsequent accepted changes produce alerts, and recovery is sent only when that channel acknowledged an unhealthy notification. Monitor and channel edits use version and association checks to reject stale changes. Gatus-managed monitors remain read-only. Dependency-based suppression is not yet available.

For email, configure a Cloudflare `send_email` binding named `EMAIL`, a verified sender in `EMAIL_FROM`, and `EMAIL_DESTINATIONS` as a JSON array of deployment-approved `{id,name,address}` entries. Restrict the binding's allowed sender and recipient addresses to the same approved values. Set `EMAIL_READY=true` and `CHANNELS_READY=true` only after configuring and verifying both the operations and probe Workers; use equivalent settings on each. Addresses stay in deployment configuration, and the application exposes only recipient IDs and names. Never commit private recipient addresses or production bindings. Disabling readiness stops delivery; changing a sender or recipient invalidates existing channel fingerprints until an administrator re-saves the channel.

Automation state is held through global and targeted maintenance. After a window, a fresh valid observation is required before a held event can proceed. Stale pending transitions are superseded, including when status cycles back to the same value. An already in-flight delivery cannot be recalled. When no trustworthy pre-window observation is retained during migration, the next valid observation establishes a new baseline rather than triggering an action.
