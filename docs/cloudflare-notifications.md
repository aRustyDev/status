# Cloudflare notification channels

The Cloudflare profile supports one notification provider: an HTTPS webhook with a Bearer token from a local Vault Secure Value. Other providers, SMTP and upstream alert-hygiene policies are unavailable. Administrators create a channel, select a deployment-approved destination and assign local monitors with checks. Gatus-managed monitors are not assignable. A channel sends when a valid check result changes between up, degraded and down. A new check’s first unhealthy result can send an alert; its first healthy result establishes a baseline without a notification. A saved channel can also send a test. The body contains the event type, check ID, status and scheduled time; it contains no credential. Recipients should treat monitor identifiers and status as operational metadata.

`CHANNEL_ENDPOINTS` is a JSON array in the same format as `ENDPOINTS`, but is a separate deployment-controlled allowlist for POST destinations. Every entry must use HTTPS, including service bindings. Each channel stores the selected endpoint's fingerprint; if its URL, binding, service ID or revision changes, attempts that observe the change fail closed until an administrator re-saves the channel. Configure bindings explicitly and review each destination: a destination receives the Vault token and event metadata. Tokens must be at most 4096 characters, use only letters, digits, hyphen, dot, underscore, tilde, plus and slash, and may have trailing equals signs. Whitespace and other characters fail closed. Do not put credentials in channel names or endpoint URLs; names are visible metadata. The API returns destination IDs and names, never endpoint URLs, tokens, response headers or bodies.

To enable channels, first follow the probe drain and migration procedure in [Cloudflare deployment](cloudflare-deployment.md), then deploy the new probe with the Vault key, `CHANNEL_ENDPOINTS` and any destination bindings, then deploy the operations Worker with the same key and equivalent endpoint configuration and bindings. Verify the endpoint IDs, fingerprints and bindings in both deployed Workers and their connectivity. Only then set `CHANNELS_READY=true` in **both** Workers and deploy them, followed by the admin UI. This explicit readiness assertion is required in addition to a valid Vault key and at least one approved endpoint; if it is missing, channels remain disabled. Removing or changing the assertion stops dispatching queued events after the configuration takes effect; it does not remove pending events or cancel in-flight requests. The operator must repeat this verification after either Worker's bindings, secrets or endpoint list change.

Events are written atomically with accepted check results to a D1 outbox containing identifiers and status, never resolved credentials or destination URLs. Dispatch resolves the current Vault value for the saved channel version immediately before sending, checks the channel and monitor versions and the destination fingerprint, sends with redirects disabled and a five-second timeout, and never records response bodies or exception messages. Subsequent lookups observe secret rotation. Missing secrets, changed/deleted channels or monitor configurations, disabled channels and destination drift observed before sending fail closed with a generic `unavailable` result. As described in the [Vault runtime contract](cloudflare-vault-runtime.md), a change after the final check can race an in-flight request. Failed requests retry on later scheduled ticks up to three attempts, using the same `Idempotency-Key` for each attempt. Pending events normally expire after one hour; events held across a maintenance window do not expire on that timer. Leases prevent concurrent Workers from normally sending the same event together, but a crash after the receiver accepts and before the sender records success can cause duplicate delivery. Receivers should honor the idempotency key. Terminal delivery records are retained for approximately 24 hours and pruned in batches of up to 500 per scheduled tick. Up to 20 deliveries are attempted per tick; monitor delivery status for capacity problems. Recent delivery states and generic error codes are visible to administrators; failed requests are not silently reported as successful.

The outbox insert shares the check-result transaction. This prevents alerts for a result that was not committed, but a missing or broken outbox table will roll back the check result while `CHANNELS_READY=true`. Apply and verify the migration before enabling readiness, and set the flag to false if the outbox is unavailable.

Maintenance suppresses new transitions for affected checks. Events queued before a window wait until a valid post-window observation; a newer transition supersedes an older pending event, including when the status later returns to the same value. Dispatch checks maintenance again before sending, but that check is a snapshot: a window activated or changed after the final check can race an in-flight send. For strict suppression, stop new dispatches and manual channel tests, and drain in-flight requests before activating or changing the window; follow the probe drain procedure in [Cloudflare deployment](cloudflare-deployment.md), including trigger propagation and invocation time. Credential-unavailable results also hold pending events until a valid observation. An up notification is sent only if the same channel configuration previously acknowledged an unhealthy status; changing the channel configuration starts a new delivery history. Migration `0010_notification_transition_state.sql` fails closed legacy pending or sending notification jobs, so inspect their states rather than expecting them to replay.
