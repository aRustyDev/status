# Cloudflare notification channels

The Cloudflare profile supports deployment-approved email recipients through a Cloudflare Email Sending binding, and HTTPS webhooks with a Bearer token from a local Vault Secure Value. Other providers, SMTP and upstream alert-hygiene policies are unavailable. Administrators create a channel, select a deployment-approved destination and assign local monitors, including those that do not yet have a check. Alerts are emitted only for enabled checks. Gatus-managed monitors are not assignable. A new check’s first unhealthy observation can alert; its first healthy observation establishes a baseline. A saved channel can also send a test. Webhook messages contain the event type, check ID, status and scheduled time; email messages contain the monitor name, status and time. Recipients should treat these as operational metadata.

After upgrading, refresh any previously open admin tabs before editing channels. Older pages lack the monitor identity and version snapshots required to save; the API rejects their saves with a refresh message rather than risking delivery for the wrong monitor.

`CHANNEL_ENDPOINTS` is a JSON array in the same format as `ENDPOINTS`, but is a separate deployment-controlled allowlist for POST destinations. Every entry must use HTTPS, including service bindings. Each webhook channel stores the selected endpoint's fingerprint; if its URL, binding, service ID or revision changes, attempts that observe the change fail closed until an administrator re-saves the channel. Configure bindings explicitly and review each destination: a destination receives the Vault token and event metadata. Tokens must be at most 4096 characters, use only letters, digits, hyphen, dot, underscore, tilde, plus and slash, and may have trailing equals signs. Whitespace and other characters fail closed. Do not put credentials in channel names or endpoint URLs; names are visible metadata. The API returns destination IDs and names, never endpoint URLs, tokens, response headers or bodies.

Before applying `0010_notification_transition_state.sql`, follow the probe drain and migration procedure in [Cloudflare deployment](cloudflare-deployment.md). The migration fails legacy pending or sending notification jobs closed because their transition generation cannot be reconstructed; inspect their states rather than expecting them to replay. For webhooks, deploy the new probe first with the Vault key, `CHANNEL_ENDPOINTS` and any destination bindings, then deploy the operations Worker with the same key and equivalent endpoint configuration and bindings. Verify the endpoint IDs, fingerprints, bindings and connectivity in both Workers. Only then set `CHANNELS_READY=true` in **both** Workers and deploy them, followed by the admin UI. Webhook availability also requires a valid Vault key and at least one approved endpoint. Removing or changing the readiness assertion stops queued delivery after the configuration takes effect; it does not remove pending events or cancel in-flight requests. Repeat the verification after either Worker's bindings, secrets or endpoint list change.

Events are written atomically with accepted check results to a D1 outbox containing identifiers and status, never resolved credentials or destination URLs. For webhooks, dispatch resolves the current Vault value for the saved channel version immediately before sending, checks the channel and monitor versions and destination fingerprint, sends with redirects disabled and a five-second timeout, and never records response bodies or exception messages. Subsequent lookups observe secret rotation. Changes after the final check can race an in-flight request; see the [Vault runtime contract](cloudflare-vault-runtime.md). Missing secrets, changed or deleted channels or monitor configurations, disabled channels and destination drift fail closed with a generic `unavailable` result. Webhook requests retry on later scheduled ticks up to three attempts, with a stable `Idempotency-Key`; receivers must deduplicate this key. Email sends are attempted at most once: an ambiguous failure or crash may lose an alert rather than risk sending a duplicate. An accepted email is not proof of inbox delivery. Pending events normally expire after one hour; events held across a maintenance window do not expire on that timer. Leases prevent concurrent Workers from normally sending the same event together. Terminal delivery records are retained for approximately 24 hours and pruned in batches of up to 500 per scheduled tick. Up to 20 deliveries are attempted per tick; monitor delivery status for capacity problems. Recent delivery states and generic error codes are visible to administrators; failed requests are not silently reported as successful.

The outbox insert shares the check-result transaction. This prevents alerts for a result that was not committed, but a missing or broken outbox table will roll back the check result while `CHANNELS_READY=true`. Apply and verify the migration before enabling readiness, and set the flag to false if the outbox is unavailable.

## Email channels and monitor Alerts

> [!WARNING]
> **Not released yet.** Email channels and monitor Alerts require a build from the `main` branch (see [Deployment](deployment.md)).

An administrator can select an approved email recipient from the Notifications page, then select that channel in a monitor's Alerts panel. Disabled channels can remain selected but send no alerts. Subsequent accepted status changes produce alerts, and recovery is sent only when the same channel configuration previously acknowledged an unhealthy notification. Changing the channel configuration starts a new delivery history. Monitor and channel edits use version and association checks to reject stale changes. Gatus-managed monitors remain read-only.

Administrators can select Cloudflare-managed monitors in the Depends on panel. A fresh, enabled dependency check that is down, degraded or affected makes the dependent monitor affected on its next observation and suppresses duplicate notifications. A missing, disabled, stale or credential-unavailable dependency does not suppress notifications. Manual status and incident impact do not determine dependency suppression. If the dependent previously sent an independent outage notification, its recovery is sent when it becomes healthy. Gatus-managed monitors cannot be selected as dependencies.

Apply `0014_monitor_alert_channel_limit.sql` after `0013_notification_unlink_cancel.sql` and before using monitor Alerts. Each channel supports up to 20 assigned monitors, including monitors without checks. Existing assignments above the limit are preserved and can be removed; no new assignment is accepted until the channel is below the limit.

For email, configure a Cloudflare `send_email` binding named `EMAIL`, a verified sender in `EMAIL_FROM`, and `EMAIL_DESTINATIONS` as a JSON array of deployment-approved `{id,name,address}` entries. Restrict the binding's allowed sender and recipient addresses to the same approved values. Set `EMAIL_READY=true` and `CHANNELS_READY=true` only after configuring and verifying both the operations and probe Workers; use equivalent settings on each. Addresses stay in deployment configuration, and the application exposes only recipient IDs and names. Never commit private recipient addresses or production bindings. Disabling readiness stops delivery; changing a sender or recipient invalidates existing channel fingerprints until an administrator re-saves the channel.

Maintenance suppresses new transitions for affected checks. Events queued before a window wait until a valid post-window observation; a newer transition supersedes an older pending event, including when the status later returns to the same value. Credential-unavailable results also hold pending events until a valid observation. Dispatch checks maintenance again before sending, but that check is a snapshot: a window activated or changed after the final check can race an in-flight send. For strict suppression, stop new dispatches and manual channel tests, and drain in-flight requests before activating or changing the window; follow the probe drain procedure in [Cloudflare deployment](cloudflare-deployment.md), including trigger propagation and invocation time. When no trustworthy pre-window observation is retained during migration, the first valid unhealthy observation alerts; a healthy observation establishes a baseline without an alert.

## Delivery history

Administrators can open Delivery History to inspect notification and action outcomes. Records contain generic error codes and never contain destination URLs, credentials, response bodies or exception text. Terminal notification and action records are retained for approximately 24 hours. Attempt details are available for notification deliveries recorded after the delivery-history migration; earlier records retain their summary. Channel test results appear in notification history. Subscriber history is unavailable until subscriber delivery is implemented.

A failed webhook delivery that exhausted its three automatic attempts can be queued for one additional attempt by an administrator while the original event, channel and monitor remain eligible. The probe applies the normal version, destination, transition, maintenance and credential checks and sends the original idempotency key. Manual retry is unavailable for email and actions, whose sends may have already taken effect. Retry requests are recorded in the audit log.
